# Разработка

## Окружение

Используем Python 3.11 и отдельную `.venv`. Команды настройки находятся в [README](README.md#быстрый-старт). Каркас использует только стандартную библиотеку. Новые зависимости добавляем по необходимости; фиксированный lockfile потребуется до сдачи вместе с проверкой установки из чистого окружения.

## Работа с изменениями

- Небольшие ветки и PR по завершённому изменению. Владельцы задач между участниками не назначены.
- Сначала согласовать изменение общего контракта, затем обновить реализацию и документацию.
- Названия модулей, публичных полей и типов ошибок — на английском; объяснения проекта — на русском.
- Не хранить реальные финансовые данные. Генерируемые приватные ответы и локальные артефакты не коммитить.
- Изменение не считается готовым только потому, что совпали ответы генератора и scorer: нужны независимые проверки по открытым записям.

## Проверки

```bash
make check PYTHON=python
```

Команда рассчитана на активированную `.venv` с Python 3.11+. Сейчас это проверка CLI, компиляции и синтаксиса примера конфигурации. Предметные тесты добавляем вместе с функциональностью по [матрице](docs/VALIDATION.md).

## Доступ к GitHub

В рабочей папке уже настроен `origin`. Перед публикацией проверить `git ls-remote origin`, удалённую историю и права записи. Сеть терминала и подключённый GitHub-плагин доступны; публикацию можно выполнить через плагин без настройки вымышленного локального автора. Для обычных локальных коммитов нужны собственные имя и email в Git, а для push — отдельная авторизация. Не использовать force push и не подменять авторство коммитов.

## Документы и реализация

Отмечать запланированные функции как запланированные. Обновлять README при появлении работающего этапа. Python Protocol и разделение модулей не обеспечивают процессную изоляцию; её нужно реализовать и проверить отдельно.
