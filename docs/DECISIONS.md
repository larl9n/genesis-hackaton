# Решения и открытые вопросы

## Принято для каркаса

| Решение | Причина |
| --- | --- |
| Python 3.11, `src`-структура пакета | Соответствие предложенному окружению и явная упаковка |
| Runtime без внешних зависимостей на старте | Минимальный каркас запускается без установки библиотек |
| CLI как основной интерфейс | Сдаче нужны среда и демонстрация; сайт необязателен |
| JSON-действия с полями `action` и `params` | Единая оболочка для будущего процесса политики |
| Генератор, среда и оценщик в отдельных модулях | Разделение предметных правил, открытых данных и приватной оценки |
| Oracle только в evaluation | Его привилегии не должны становиться доступными обычным политикам |
| Деньги в minor units, FX через Decimal | Явные валюты и контролируемое округление |
| Генерируемые артефакты вне Git по умолчанию | Не смешивать исходники, большие наборы и закрытые ответы |

Build-зависимость setuptools пока задана диапазоном в pyproject; фиксированный lockfile появится на этапе упаковки. `configs/clean.json` загружается и проверяется текущим CLI. `configs/default.json` остаётся образцом будущего конфига с ошибками.

## Зафиксировано при реализации чистой модели

- Публичные runtime-схемы реализованы строгими dataclass-моделями стандартной библиотеки, не TypedDict-проверкой.
- Счета содержат целые количества и цены; total равен сумме позиций.
- Распределения платежа имеют invoice_id, allocated_minor и явную currency.
- Период `[start,end)`, признание счета по issued_at. CSV null — литерал `null`.
- Счета учета текущей модели: receivable, revenue, bank. Проверяющий восстанавливает проводки по документам, не использует генератор или provenance.
- Экспорт чистых данных возможен только после успешной проверки. Повторная запись в существующую папку запрещена.
- По требованию пользователя после каждого этапа запускаются функциональные проверки; результаты фиксируются в CHECKPOINTS.md.

## Зафиксировано для первых ошибок и эпизода

- Дубль — повторное признание одной документированной продажи; affected ID — invoice_id, сумма — лишнее признание один раз.
- Ошибка платежа — недостаточный кредит receivable с той же суммой ошибочного revenue; affected IDs — invoice_id и payment_id. Полное отсутствие и частичный дефект настраиваются отдельно.
- Эталон независимо проверяется только по public, восстановлением чистых проводок; provenance не является источником правильности проверки.
- IDs — case-sensitive множества; отдельные повторные находки не удаляются и дают FP. Сопоставление — детерминированное максимальное двудольное matching, не жадный первый матч.
- AuditEnv реализует reset/step и маскирование награды evaluation в одном процессе. Это development-режим, а не безопасный held-out стенд.
- Oracle demo принадлежит оценщику; его высокий score не считается результатом агента. Конфиг двух семейств — configs/scenario.json.

## Нужно решить перед реализацией

- Формат IPC, политика лимитов на сообщения и реальная изоляция процесса на Linux.
- Межпроцессное применение уже реализованной сериализации step и маскирования reward в train/evaluation, ограничения host API.
- Выбор лицензии и фиксированных build/runtime зависимостей до сдачи.

## Реализовано в версии 0.2.0

- Публичная схема v0.2 разрешает отрицательные платежи и распределения возврата. Старые положительные записи v0.1 поддержаны, но возвраты под старой версией отклоняются. Конфиги v0.1 принимаются в прежней форме без новых включённых ошибок.
- Счета и проводки выражены в базовой валюте, иностранные поступления оцениваются по локальной дате платежа в manifest.timezone. Разрядности и HALF_EVEN/HALF_UP проверяются; переоценка валютного остатка не моделируется.
- Документы вне отчётного периода допустимы; проводки в чистой книге создаются только в полуоткрытом периоде. Начальные остатки не включаются в движения периода.
- Возврат — отрицательный payment/ref с обратными проводками. Достаточность уже полученных сумм проверяется по времени, а не только итоговым неттингом.
- Семантика сумм, targets и evidence для всех четырёх семейств и двух композиций определена в ISSUES.md. Counts включают совместные targets; скрытых дополнительных labels нет.
- Исправлены два воспроизведённых сбоя: переполнение календаря у края диапазона и незавершение malformed submit без params. Регрессионные тесты обязательны в общем наборе.

## Организационные уточнения

- Точное время дедлайна до 20 ноября и последние изменения регламента.
- Правила публикации открытых train/dev fixtures и закрытых данных оценщика.
- Реальная доступность официального стенда организаторов. Не объявлять собственные тесты официальной проверкой.
