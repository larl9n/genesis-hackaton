# Данные и доказательства

Статус: engine/config/public v0.2 с поддержкой прежних положительных данных и конфигов v0.1. [configs/clean.json](../configs/clean.json) — прежний чистый пример. [full.json](../configs/full.json) и [interactions.json](../configs/interactions.json) — работающие полные конфиги. [configs/default.json](../configs/default.json) — неиспользуемый проект первоначальной формы, не принимается этими генераторами.

Runtime-модели: [domain/models.py](../src/genesis_fintech/domain/models.py). Проверка проводок по открытым документам: [evaluation/clean.py](../src/genesis_fintech/evaluation/clean.py). Классы проверяют типы и поля при загрузке; межзаписные ссылки и бухгалтерские соответствия проверяются отдельно.

## Реализованная модель чистой компании

- Одна базовая валюта книги, счета в ней же, платежи могут быть иностранными. Поддержаны KZT/USD/EUR с разрядностью 2, JPY с 0, KWD с 3. В manifest объявлены разрядности всех используемых валют.
- 1–60 счетов для примеров, по умолчанию 50. Официальный ориентир размера соблюдается стандартной конфигурацией; маленькие примеры используются только в разработке и тестах.
- Счёт: дебет `receivable`, кредит `revenue` на `total_minor`, если issued_at внутри `[start,end)`. Документы вне периода остаются доступными, но их движения в книгу текущего периода не добавляются.
- Платёж: дебет `bank` на базовую оценку, кредит `receivable` на каждое распределение, если дата платежа в периоде. Банковская строка содержит `payment_id` и `invoice_id=null`. Валютная оценка выбирает точную котировку на дату платежа в manifest.timezone и использует Decimal с объявленным округлением; отсутствие/дубли котировки не угадываются.
- `line_items`: объекты `{description, quantity, unit_price_minor}`. Итог счёта точно равен сумме quantity × unit_price_minor.
- `invoice_refs`: объекты `{invoice_id, allocated_minor, currency}`. Сумма распределения задана в валюте счёта/базовой книге, не в иностранной валюте платежа; сумма распределений равна явно конвертированной оценке.
- Разбитые и частичные платежи допустимы. Возврат — отрицательные amount_minor/allocated_minor; банк кредитуется, receivable дебетуется. Ноль запрещён, знаки документа и распределений должны совпадать. До возврата должны существовать достаточные поступления: будущим платежом ранний возврат не оправдывается. Одновременные события проверяются общей суммой на один timestamp.
- Генератор создаёт возвраты в базовой валюте и не больше ранее оплаченной суммы. В этой ограниченной модели накопленное распределение на каждый timestamp также не должно превышать сумму счёта; будущий возврат не скрывает прежнюю сверхаллоцированную сумму. Непогашенная задолженность и правильные отрицательные платежи сами по себе не ошибки. Авансы сверх суммы счёта, нераспределённые поступления, иностранные счета и переоценка остатков не моделируются.
- Суммы ограничены модулем `10^15` minor units, bool и float в денежных полях запрещены. JSON с дублирующимися ключами, NaN/Infinity и неизвестными полями отклоняется.
- Seed, конфиг, исходная история и пустой список изменений сохраняются в private/provenance.json. Чистый truth: `{episode_id, issues: []}`. `load_public` читает только шесть фиксированных открытых файлов.

Clean checker и reward matcher имеют разные роли и оба реализованы. Проверка этой ограниченной синтетической модели не является заключением о произвольных реальных книгах.

## Генерация

1. Создать согласованную скрытую историю операций компании.
2. Проверить бухгалтерские равенства и связность до ошибок.
3. Получить счета, платежи, курсы и проводки из общей истории.
4. Внести выбранные причинные изменения и записать их в provenance.
5. Создать truth, указывающий реальное расхождение и достаточные открытые доказательства.
6. Независимо проверить truth по открытым документам, а не только по журналу внесённых ошибок.

Seed, номера ошибок, их количество и параметры инъекции не входят в публичный manifest. В примере конфигурации они доступны управляющему процессу, а не политике.

## Открытые файлы

| Файл | Поля по ТЗ |
| --- | --- |
| `manifest.json` | `schema_version`, `episode_id`, `base_currency`, `period_start`, `period_end`, `timezone`, число записей/документов, правила округления и допусков |
| `ledger.csv` | `row_id`, `timestamp`, `account`, `debit_minor`, `credit_minor`, `currency`, `entity_id`, `invoice_id`, `payment_id` |
| `invoices.jsonl` | `doc_id`, `invoice_id`, `entity_id`, `issued_at`, `due_at`, `currency`, `total_minor`, `line_items` |
| `payments.jsonl` | `doc_id`, `payment_id`, `timestamp`, `currency`, `amount_minor`, `invoice_refs` |
| `fx.csv` | `date`, `source_currency`, `target_currency`, `rate` |
| `policy.json` | Правила выбора даты FX, включения в период и округления |

Ориентиры размера: 200–2000 проводок, 20–200 документов, 0–12 ошибок. Генератор должен проверять, что выбранная конфигурация выполнима и доказательства доступны в пределах инструментов и бюджета.

## Деньги и время

- Суммы — целые minor units; показатель разрядности каждой используемой валюты публикуется в manifest. Отклонять bool и дробные значения в целочисленных полях.
- FX — десятичные строки, расчёты через `Decimal`; точность и округление задаёт политика.
- Разные валюты не складываем и не сравниваем без явной конвертации.
- Временные метки — ISO-8601 со смещением; границы периода интерпретируются в объявленном часовом поясе.
- Граница периода — `[period_start, period_end)`, опубликована в policy как `[start,end)`; крайняя правая дата исключена.
- В JSON отсутствие ссылки — `null`. В CSV используется литерал `null`; пустые ссылки не угадываются, а отклоняются. Точный round-trip проверяется тестами.

## Закрытые файлы

| Файл | Содержание |
| --- | --- |
| `truth.json` | `issue_id`, `type`, `affected_ids`, `expected_amount_minor`, `currency`, допустимые наборы доказательств |
| `provenance.json` | История генерации и точные причинные изменения |

Для воспроизведения seed и полная конфигурация хранятся отдельно в приватных метаданных запуска. Политика их не видит.

ID не кодируют наличие ошибки: episode/entity/invoice/payment/doc/row и 128-битное значение из локального RNG. FX evidence ID: `fx_<YYYY-MM-DD>_<SOURCE>_<TARGET>`, отдельная колонка CSV не нужна. Канонизация affected IDs реализована. Только clean truth пуст; сценарный truth содержит независимо подтверждённые issues.

`acceptable_evidence_sets` — реализованное поле: список наборов ID. Для TP нужен хотя бы один набор целиком. Пустые наборы запрещены. Все ID должны разрешаться в открытые записи, достаточные для проверки расхождения. Определения четырёх семейств и взаимодействий — в [ISSUES.md](ISSUES.md).

## Семейства ошибок

| Внутренний тип v0.1 | Что должно быть доказуемо |
| --- | --- |
| `duplicate_invoice` | Дублирование одной операции, а не просто одинаковые суммы |
| `payment_allocation` | Разница между подтверждённым платежом и отражённым распределением |
| `fx_mismatch` | Неверный курс или дата относительно опубликованной политики |
| `period_cutoff` | Ошибка признания в периоде по открытым временным данным и policy |

Все четыре семейства реализованы. Две композиции — fx_allocation и duplicate_cutoff — совместно меняют одно событие/пачку проводок; простое наличие независимых дефектов в разных счетах взаимодействием не считается.

## Траектории

Требуемые поля JSONL: `episode_id`, `step`, `action`, `observation`, `reward`, `terminated`, `truncated`. Наблюдение не включает truth или seed. В evaluation полный лог наград остаётся у оценщика; экспорт для политики не должен раскрывать закрытую диагностику. Воспроизводимость проверяем по содержательным полям, а время исполнения храним как отдельную диагностику.
